# GMT Collection Builder

A small R tool that builds `.gmt` gene-set files for GSEA/ssGSEA from [MSigDB](https://www.gsea-msigdb.org/gsea/msigdb), using two plain-text files (a whitelist and a blacklist) to control which pathways go in - instead of hardcoding gene set names inside an R script every time you want to change the panel.

If you've ever maintained a GSEA gene-set panel by editing R code directly, copy-pasting gene set names in and out of a vector, this replaces that with: edit a text file → run a script → get your `.gmt`.

## What this actually does

MSigDB has tens of thousands of gene sets across a dozen+ collections (Hallmark, Reactome, KEGG, WikiPathways, GO, oncogenic signatures, immunologic signatures, etc.). Most analyses don't want all of them - you want a curated subset relevant to your biology, and you want to be able to look at *why* something is or isn't in your panel, and add or remove individual pathways without re-deriving the whole thing from scratch.

This tool does that in two stages:

1. **Collection-level filter** - which MSigDB collections are even in scope (e.g. "Hallmark, Reactome, KEGG, WikiPathways - not GO, not miRNA targets"). This is coarse and changes rarely, so it lives in the script's config, not a note file.
2. **Biological keyword filter** - within those collections, which specific pathways matter to you, expressed as simple keywords/patterns (e.g. `MAPK`, `APOPTOS`, `CELL_CYCLE`) in two editable text files: a whitelist (include) and a blacklist (always exclude, even if whitelisted).

The result of both filters is written to a CSV you can review and hand-edit - flip pathways on/off, delete rows, or add a pathway by name that no pattern happened to catch - before the final `.gmt` is built from *that* CSV, not from the filters directly. This means a one-off manual decision survives independently of whatever the whitelist/blacklist say.

## Requirements

- R (any recent version)
- Two CRAN packages:

```r
install.packages(c("msigdbr", "dplyr"))
```

- No internet access needed at run time - `msigdbr` bundles MSigDB data locally as part of the package install.
- Tested with recent `msigdbr` versions; the script auto-detects whether your installed version uses the older `gs_cat`/`gs_subcat` column names or the newer `gs_collection`/`gs_subcollection` names, so either works.

| File | Purpose |
|---|---|
| `Build_GMT.rmd` | The script. Open it in RStudio/Positron and run its chunks in order (see below). |
| `gmt_whitelist.txt` | Biological keywords/patterns to include, one per line. |
| `gmt_blacklist.txt` | Biological keywords/patterns to always exclude, one per line - wins over the whitelist. |

## Quick start

1. Clone this repo.
2. Open `Build_GMT.rmd` in RStudio or Positron.
3. In the **CONFIG chunk** near the top, change `base_dir` to wherever you cloned this repo (it's an absolute path - there's no way for the script to guess this automatically). Set `species` if you're not working with human data.
4. Run the CONFIG chunk, then **Section 1**. This reads the whitelist/blacklist and writes `pathway_list.csv`.
5. Open `pathway_list.csv` and review it. Edit freely.
6. Run **Section 2**. This reads `pathway_list.csv` and writes the GMT(s) to `output/gmt/`.

That's the whole loop. Steps 5-6 repeat any time you just want to change which rows are included, without re-running Section 1.

## Full walkthrough

### Step 1: decide what you want in scope

Open `gmt_whitelist.txt`. Each line is a pattern - a plain keyword or a small regex - matched case-insensitively as a substring against MSigDB's gene set name (`gs_name`). A full exact name (e.g. `HALLMARK_HYPOXIA`) is a valid line too - it's just a pattern that happens to match only itself. Lines starting with `#` are comments; blank lines are ignored.

You don't need to prefix patterns with a collection name like `HALLMARK_` or `REACTOME_` - which collections are searched at all is controlled separately (see below), so a bare keyword like `MAPK` will be checked against every gene set name in whatever collections are already in scope.

Open `gmt_blacklist.txt` the same way. Anything matching a blacklist line is dropped even if it also matched the whitelist - **the blacklist always wins**. Use this for pathways you know are noisy, redundant, or off-topic once you've actually looked at real output.

### Step 2: run Section 1

This pulls the *entire* MSigDB table for your chosen species via `msigdbr`, then filters it:

1. By collection (`collection_whitelist_patterns`/`collection_blacklist_patterns` in the CONFIG chunk - which collections exist at all).
2. By your `gmt_whitelist.txt` patterns (keep if any line matches).
3. By your `gmt_blacklist.txt` patterns (drop if any line matches, regardless of step 2).
4. By gene-set size (`min_set_size`/`max_set_size` - drops sets that are too small to be specific or too large to be meaningful).

The result is written to `pathway_list.csv`, one row per surviving gene set, with `include = TRUE` by default and a `matched_whitelist_pattern` column showing you which line pulled each row in - useful for spotting an overly broad pattern.

The script prints a summary: how many sets survived, how many got dropped at each stage (and their names, for the blacklist/size stages), and which whitelist patterns matched *nothing at all* - almost always a typo worth checking.

**If `pathway_list.csv` already exists, Section 1 will not overwrite it.** It writes `pathway_list_draft.csv` instead, so a re-run to pick up whitelist/blacklist edits never silently destroys manual work you've already done in the real CSV. Diff the two and merge whatever you want by hand.

### Step 3: edit the CSV

Open `pathway_list.csv` in Excel, a text editor, or R. You can:

- Set `include` to `FALSE` on any row to drop it without deleting it (keeps the row as a record of "considered, rejected").
- Delete a row entirely.
- Add a new row for any MSigDB gene set you know by name that no pattern happened to catch. **You only need to fill in `include` and `gs_name`** - the next time Section 2 runs, it looks up `gs_cat`, `gs_subcat`, `n_genes`, and `gs_description` from `msigdbr` and writes them back into the CSV for you. It only fills in genuinely blank cells - anything you've already typed (including your own notes in the `notes` column) is left untouched.

### Step 4: run Section 2

This reads `pathway_list.csv`, takes every row with `include = TRUE`, and re-fetches each gene set's actual member genes from `msigdbr` by exact name (the CSV itself only stores metadata, not the gene list - this is what makes manual CSV edits actually take effect). It writes:

- `output/gmt/<out_name>.gmt` - one GMT containing every included pathway
- `output/gmt/individual/<gs_name>.gmt` - the same pathways, one file each, for tools/workflows that expect one gene set per file

If a `gs_name` in your CSV doesn't actually exist in `msigdbr` for the configured species (a typo, a renamed set, or the wrong species selected), it's skipped and reported by name rather than silently dropped or erroring out.

## Note file format (`gmt_whitelist.txt` / `gmt_blacklist.txt`)

- One pattern per line.
- Case-insensitive substring/regex match against `gs_name`.
- Exact names and loose patterns can be mixed freely in the same file.
- `#` starts a comment; blank lines are ignored.
- Blacklist beats whitelist, always - there's no way to force-include something the blacklist also matches other than removing/editing the blacklist line.

## `pathway_list.csv` columns

| Column | Meaning |
|---|---|
| `include` | `TRUE`/`FALSE` - whether this row goes into the GMT. Along with `gs_name`, the only column Section 2 actually requires. |
| `gs_name` | Exact MSigDB gene set name. |
| `gs_cat` / `gs_subcat` | MSigDB collection/subcollection (e.g. `C2` / `CP:REACTOME`). Auto-filled if you leave it blank on a new row. |
| `n_genes` | Gene count as of generation time. Auto-filled if blank. |
| `matched_whitelist_pattern` | Which whitelist line pulled this row in. Empty for rows you added by hand. |
| `gs_description` | MSigDB's own description of the gene set. Auto-filled if blank. |
| `notes` | Free text, entirely yours. Never touched by the script. |

## Configuration reference

All in the CONFIG chunk at the top of `Build_GMT.rmd`:

| Variable | Meaning |
|---|---|
| `species` | Anything `msigdbr` supports, e.g. `"Homo sapiens"`, `"Mus musculus"`. |
| `base_dir` | Absolute path to wherever you cloned this repo. **Change this first** - it's the one thing the script can't infer. |
| `pathway_csv` | Path to the working CSV. Defaults to `base_dir/pathway_list.csv`. |
| `Out_dir` | Where output lands. Defaults to `base_dir/output`; point it at a specific project's folder if you want the GMT to live there instead. |
| `out_name` | Filename for the joint GMT. |
| `min_set_size` / `max_set_size` | Gene-count bounds for what counts as a usable pathway. Defaults 10/250. |
| `collection_whitelist_patterns` / `collection_blacklist_patterns` | Which MSigDB collections are in scope at all, checked against `gs_cat:gs_subcat` (e.g. `C2:CP:REACTOME`). Defaults to Hallmark + Reactome + KEGG + WikiPathways + Reactome Medicus, excluding GO:CC, miRNA targets, and TFT targets. |

```
        ├── KEGG_CELL_CYCLE.gmt
        └── ...
```

## Troubleshooting

- **`Column 'gs_cat' doesn't exist`** - a recent `msigdbr` version renamed this column to `gs_collection`. The script already detects and handles both; if you still hit this, your installed `msigdbr` is using yet another schema and `resolve_col()` in the CONFIG chunk needs another candidate name added.
- **`cannot open file '.../gmt/....gmt': No such file or directory`** - almost always means `Out_dir` points somewhere that doesn't exist (a network drive that isn't mounted, a typo). Also check you re-ran the CONFIG chunk after editing it - R keeps old variable values in memory until you re-run the chunk that sets them, so editing the file alone doesn't update a value you've already loaded into your session.
- **A pathway you expected is missing** - check the Section 1 summary output for "dropped by collection allow/block list", "dropped by blacklist", and "dropped by size filter". Also check `gmt_blacklist.txt` for an overly broad pattern (e.g. a 2-3 letter keyword can match substrings inside unrelated gene set names).
- **A whitelist pattern "matched nothing"** - reported explicitly by Section 1. Usually a typo, or the collection it belongs to isn't in `collection_whitelist_patterns`.

> Liberzon A, Birger C, Thorvaldsdóttir H, Ghandi M, Mesirov JP, Tamayo P. The Molecular Signatures Database (MSigDB) hallmark gene set collection. *Cell Systems*. 2015;1(6):417-425.

KEGG: Kyoto Encyclopedia of Genes and Genomes. *Nucleic Acids Research*. 2000;28(1):27-30. **KEGG's license is not fully open** - free for academic/non-commercial use, but commercial use requires a license from Kanehisa Laboratories/Pathway Solutions. ## Citing this repository

This repo ships a [`CITATION.cff`](CITATION.cff) file, which is GitHub's standard machine-readable citation format - once it's in the repo, GitHub automatically shows a **"Cite this repository"** button on the repo's main page (top right, near "About"), which generates APA and BibTeX for you and stays in sync if you edit `CITATION.cff`. That's the recommended way for anyone using this to get a citation - it's always current with whatever's in the file.

For quick reference, here are the same details in a few common formats:

**Plain text:**
> Balagopal, N. K. (2026). *GMT Collection Builder* [Computer software]. GitHub. https://github.com/navinvent/GMT_Collection_Builder

**APA:**
> Balagopal, N. K. (2026). *GMT Collection Builder* (Version 1.0.0) [Computer software]. GitHub. https://github.com/navinvent/GMT_Collection_Builder. ORCID: [0000-0002-3012-2469](https://orcid.org/0000-0002-3012-2469)

**BibTeX** (`@software` - if your BibTeX style doesn't support the `software` entry type, e.g. plain `bibtex` rather than `biblatex`, use `@misc` instead, shown second):

```bibtex
@software{balagopal_2026_gmt_collection_builder,
  author  = {Balagopal, Navin Kumar},
  title   = {{GMT Collection Builder}},
  year    = {2026},
  url     = {https://github.com/navinvent/GMT_Collection_Builder},
  version = {1.0.0}
}
```

```bibtex
@misc{balagopal_2026_gmt_collection_builder,
  author       = {Balagopal, Navin Kumar},
  title        = {{GMT Collection Builder}},
  year         = {2026},
  howpublished = {\url{https://github.com/navinvent/GMT_Collection_Builder}},
  note         = {Version 1.0.0}
}
```

**One more option worth knowing about:** if you want this tool to have a permanent, versioned citation with its own DOI (common for research software people actually depend on, and required by some journals for "software availability" statements), you can archive a GitHub release through [Zenodo](https://zenodo.org) - link your GitHub account, flip the switch for this repo, then cut a release (a git tag) on GitHub. Zenodo mints a DOI for that exact release automatically and it's citable forever, independent of whether the GitHub repo changes or disappears later. Not set up yet here since there hasn't been a tagged release.
